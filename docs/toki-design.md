# Toki: 時間記録アプリの設計

日付: 2026-09-23
状態: Phase 38の計測画面までローカル実装。カレンダー・PWA・本番提供は未着手。
関連: [フェーズ計画](toki-roadmap.md)、[ADR-0021](decisions/0021-toki-independent-product.md)

## 1. 目的と確定した範囲

ストップウォッチまたはタイマーで計測した時間に、後から行動内容を付け、アプリ内カレンダーで振り返る。所有者が確認したPC・スマートフォン画面案を実装の基準とする。2026-09-23に正式な製品名を`Toki`、開発先をPublic `Rizakura0110/toki`と確認した。Cloudflare resource名・IDは本番作成前に確定する。

- ストップウォッチは経過時間、タイマーは残り時間を表示する。どちらも一時停止は設けない。途中終了は可能とする。
- 計測終了後に内容を入力して保存する。**保存された記録だけ**をアプリ内カレンダーに表示する。入力前・未保存の計測はカレンダーに表示しない。
- 保存済み記録の開始・終了日時と内容を編集できる。変更後の所要時間を再計算し、カレンダー上の位置へ反映する。
- 計測中は任意で「時間だけ表示」に切り替えられる。計測値だけを画面の中心に大きく表示し、数値のタップ/クリックまたは`Esc`で通常画面へ戻る。切り替えによって計測は止まらない。
- PCは週・日カレンダー、スマートフォンは計測・カレンダーの主要画面と日タイムラインを用意する。キーボード操作、読み上げ、文字拡大を含めて検証する。
- スマートフォンではToki専用PWAとしてホーム画面から起動できるようにする。既存のTech Inbox・DaymarkのPWA identityには干渉しない。

## 2. 操作と状態の流れ

| 状態 | 操作・イベント | 結果 |
|---|---|---|
| 待機 | ストップウォッチ開始 / タイマー時間を指定して開始 | サーバーで開始時刻とモードを確定し、`running`へ |
| `running` | 時間だけ表示 / 通常画面へ戻る | 見た目だけ変わり、計測は継続 |
| `running` | 終了 | サーバーで終了時刻を確定し、`awaiting_description`へ |
| `running`のタイマー | 設定した期限に到達 | 終了時刻は期限で確定し、`awaiting_description`へ。画面を閉じていても復帰時に同じ結果を再構成 |
| `awaiting_description` | 内容を入力し保存 | 完了記録となり、カレンダーへ表示 |
| `awaiting_description` | 破棄 | 未保存計測を終了し、カレンダーには追加しない |
| 保存済み | 日時・内容の編集 | 再計算した時間と配置を更新 |

計測表示の秒数は端末内で更新し、毎秒のAPI通信・DB書き込みは行わない。開始・停止・保存・破棄・編集などの状態変更、画面起動/復帰時の未完了状態取得、必要な期間のカレンダー取得だけを通信する。開始・終了・期限の確定時刻はサーバー側を正とし、端末時計が変わっても保存値を変えない。画面表示は確定時刻と現在時刻の差から再計算し、`setInterval`の回数を実績として保存しない。

タブ/PWAを閉じても`running`または`awaiting_description`をサーバー側に保持する。再起動・別端末では同じ未完了状態を取得して復帰する。タイマー満了時にブラウザ通知・Cloudflareの定期実行・バックグラウンド処理が必ず動くことは前提にしない。再取得時にも期限超過を判定し、計測は期限で止める。途中終了は実際の終了時刻を使う。通信失敗時は「保存未確認」を明示し、成功したと見せかけたり別の計測を自動開始したりしない。

同じ本人でも2タブ/2端末からの操作があり得る。初期版では計測の置き忘れ・二重計測を防ぐため、DBで`running`/`awaiting_description`の未完了計測を合計1件までに制限し、新規開始時に既存状態を返すか競合を表示する。前日の入力待ちが残っている場合も、起動時に保存/破棄の選択を示し、それを解決してから新規計測を始める。これは画面上で理由と復帰導線を明示する初期仕様であり、複数の入力待ちを許す拡張が必要になれば別途見直す。重複送信でも二重記録を作らないよう、状態遷移と保存を冪等に扱う。記録編集と並行操作では更新競合を検出し、静かに他方を上書きしない。

## 3. 記録とカレンダー

- 計測セッションと保存済み記録を区別する。最小限の永続項目はモード、開始時刻、タイマー設定秒数/期限、状態、終了時刻、内容、更新版数。具体的なschema/API DTOはPhase 37で確定し、migrationとテストに固定する。
- 時刻はUTCの瞬間として保存し、初期表示の暦日・週・編集入力は`Asia/Tokyo`で扱う。週は月曜始まり。夏時間のある端末設定に引きずられない。
- 開始時刻より終了時刻が後であること、時間長・内容長・検索期間が安全な上限内であることを検証する。日をまたぐ1件はデータとして分割せず、各日のタイムラインにまたがる部分を描画する。
- 日・週の取得は、期間内に開始した記録だけでなく、期間と**重なる**記録を含める。期間境界は半開区間で統一し、終了境界だけが一致する記録を次期間へ重複表示しない。
- 編集後は所要時間を再計算し、変更後の日時で再取得すれば移動先に表示される。**保存済み記録の時間帯の重複は許可する**。所有者がPhase 37着手時に選択した仕様であり、カレンダーでも重複を隠さず表示する。一方、未完了の計測は1件までに制限する。
- タイマー設定は1秒〜24時間、内容は前後の空白を除いて1〜500文字、保存・編集した1記録の長さと取得期間は最大366日とする。編集は現在の`version`を送信し、他の画面で先に変更されていた場合は`409`を返す。画面は再読込してから再編集を促す。
- 最初のリリースでは外部カレンダー連携、共有、複数ユーザー、通知の到達保証、データ分析・請求機能を含めない。バックアップ/復元を追加する場合は別フェーズとして形式と競合時の動作を設計する。

## 4. 配置と認証の境界

```text
本人のブラウザ / Toki専用PWA
  └─ Toki用 Cloudflare Access application
       └─ Toki Worker（静的画面 + 保護API）
            └─ Toki専用 D1

rizakura-hontai入口 ──通常のリンク──▶ TokiのURL
Tokiのナビゲーション ──通常のリンク──▶ rizakura-hontai入口
```

Tokiは**別repository・別Worker・別D1**の独立製品とする。基盤のメニューに入口を置くが、既存Workerへの製品submodule統合、既存の`rizakura-hontai` D1への業務table追加、製品間の直接SQL/API連携はしない。共通に必要な認証の考え方・UI設計は文書とテストで揃え、実行時に基盤Workerが必須となる依存は作らない。これによりToki側の障害・migration・deployを既存2製品から切り離す。ただしCloudflareアカウント全体のFree使用量は共有する。

AccessはToki originを本人のemailに限定する別applicationを予定し、Toki Workerでもそのapplication固有のissuer・audience・本人emailを検証する。ブラウザから別製品のAPIを横断して呼ばず、単純なページ遷移だけを使う。認証前の画面/APIを漏らさない、入力と出力を検証する、安全なログと更新系のOrigin/CSRF対策を持つ。本番でのAccess application・Worker・D1作成およびdeployはPhase 43に範囲を明示して承認を得た後に行う。

Phase 37のAPIは`/api/v1/session`の取得・開始、`/api/v1/session/:id/stop|save|discard`、`/api/v1/records?startMs=&endMs=`の期間取得、`PATCH /api/v1/records/:id`の編集を持つ。時刻DTOはUTC epoch milliseconds、取得期間は半開区間。開始時の`clientRequestId`で再送を冪等化する。APIはAccess JWTをWorkerでも検証し、更新系は同一Origin、JSON、専用クライアントヘッダーを要求する。ローカル開発用の認証バイパスは明示的な起動引数とloopback HTTPの両方が揃う場合だけ有効。本番設定には入れない。

## 5. Free運用と検証の境界

毎秒更新は端末内、画面復帰時の未完了状態取得は1回、カレンダーは期間指定の取得と時刻索引による範囲検索に限定する。Worker/D1へのリクエスト数、CPU、読み書き行数、保存容量を実装時のテストと本番前確認で評価する。新しいWorker/DB/Access applicationを設けても同一アカウント内の枠は合算されるため、利用量とプランを本番作成前に再照合する。上限到達を無条件に有料プランへ切り替える運用はしない。参照: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)、[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)、[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)。

Phase 35では文書のみを変更する。新repository、Cloudflare resource、本番データ、既存2製品のruntimeとPWAは変更しない。
